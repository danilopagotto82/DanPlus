## Drive e autoridades

show_watched é uma preferência booleana local por perfil do ScoutStore. Ela participa do backup manual e ficou fora dos serviços de ProfileSettingsSync e ScoutRatingSync. O envelope v3 também preserva as três preferências anteriores. Prefira arquivo v3 com provisionamento próprio. Os protótipos v1/v2 não tiveram ativação real. A matriz registra as autoridades por campo. Coleções, Destaque Especial, apresentação, preferências portáteis de áudio/legendas já cobertas e histórico permanecem sob os serviços atuais. As configurações técnicas, tokens e credenciais ficam fora do Drive automático. O backup manual mantém Seekr no envelope autenticado.

O proprietário criou o projeto isolado DanPlus Drive Test e a Drive API foi habilitada. Para concluir o OAuth, o projeto precisa de branding, contatos, público externo em teste, usuário de teste, escopo drive.appdata e cliente TVs e dispositivos de entrada limitada. O JSON do cliente deve ficar em pasta privada. O projeto exige consentimento da conta de teste antes de qualquer prova real.

A documentação do Google admite drive.appdata no fluxo de entrada limitada e permite criar arquivos em appDataFolder. A documentação de files.update consultada não comprova a aceitação da condição If-Match no upload e a unicidade por perfil no provisionamento. O transporte v2 existente simula ETag e resposta 412. Antes de ligar o app, dois clientes autorizados precisam provar que a segunda escrita usando a mesma revisão é rejeitada, verificar conteúdo depois de cada escrita, e testar primeira conexão concorrente e recuperação. Se a API ignorar a condição, manter HOLD e escolher um protocolo sem substituição destrutiva ou outro mecanismo oficial de coordenação. [OAuth para TV](https://developers.google.com/identity/protocols/oauth2/limited-input-device) · [appDataFolder](https://developers.google.com/workspace/drive/api/guides/appdata) · [files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update)

## Prova real do fluxo de TV com Google Drive

O endpoint de código de dispositivo retornou HTTP 400 com invalid_scope para drive.appdata e HTTP 200 para drive.file com o mesmo cliente de TV. Depois do consentimento explícito do usuário de teste, o grant drive.file permitiu criar um arquivo fictício no espaço normal do Drive, localizá-lo pela API e recuperar o conteúdo byte a byte. O arquivo fictício permanece no Drive para inspeção. O teste não acessou backups pessoais.

A decisão é manter o Google Drive como destino candidato para a recuperação manual de arquivos de backup criptografados. Usar arquivos independentes por exportação evita substituir o último backup. O escopo drive.file permite acesso a arquivos criados pelo app ou disponibilizados a ele pelo usuário. O teste cobriu um cliente, e a implementação Android, a recuperação entre aparelhos, o armazenamento seguro de tokens e a sincronização automática ainda precisam de validação. A hipótese do appDataFolder fica fora dessa rota. [Escopos Drive](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)
